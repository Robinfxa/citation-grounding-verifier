| 自查问题 | 一分钟答案应包含什么 | 代码或证据入口 |
| --- | --- | --- |
| 1. 为什么不是看到真实 quote 就判 S？ | 逐字匹配只证明出处，可能主体、时间、数值、条件不对；语义蕴含由另一个层面评价 | `contracts.validate_report`；`scoring.evidence_covered`；语义审查 policy |
| 2. 未提到为什么不等于 C？ | C 需要同范围直接反证；既没有支持又没有反证是 U。外部常识不能替代给定 context | `prompts.JUDGE`；C/U 标注理由 |
| 3. 原子事实拆粗或拆细怎样影响分数？ | 合并隐藏局部错误、难以独立标注；重复/过拆可能增加 predicted 与 extra；gold 也可能漏掉因果句中单独断言的事件 | `score_case`；审查的 merged/split/duplicate 规则 |
| 4. 怎样识别 strict 误扣正确改写？ | 查看 missing/extra 原文；先不看标签做语义对齐；保留严格原分数，用预选 audit 子集报告差异，不补 test aliases | `audit.check_alignment`；锁定记录 |
| 5. evidence_sets 如何表达组合？ | 外层备选组是 OR；一个组中所有引文是 AND。缺跨段实体链接就可能不够 | `evidence_covered` 的两层匹配 |
| 6. gold 为什么不能传给端到端 verifier？ | 会预先告诉它要找哪些事实，抽取任务泄漏成 oracle；两条轨道只各测自己的输入合同 | `run_benchmark` 构造两个实际输入的分支 |
| 7. source-family split 为什么优于随机行？ | 同篇文章/版本/改写共享信息，分开会泄漏；两个答案不是两个独立来源。topic-disjoint 也不等于 project-disjoint | `Case.family_id`；manifest；来源与近重复记录 |
| 8. 旧高分为什么不够？ | 旧案例短、虚构、事实少，数据分布窄；426 测试通过不证明语义质量；改变数据后的分数不等于模型进退 | v1 报告与新版数据卡 |
| 9. 哪项优化有受控证据？ | 只能用本轮已完成 ablation 的 dev IDs、单一变化、固定条件、资源和回归回答。若尚未完成，应明确“没有新受控结论”；旧 v1→v2 不能替代 | 本轮协议及实际 ablation 结果；当前未完成时保持 pending |
| 10. 为什么 minimal/optimized 共用安全边界？ | 比较方法不能靠一方接受假引文或隐藏失败获胜；optimized 的额外调用和有限 repair 是明示的方法成本 | `_structured`、`_attempt`、`validate_report` |
| 11. timeout/schema failure 与 U 的区别？ | 前者没完成可信操作，返回错误并留在失败分母；U 是成功操作的语义判断，含义是给定材料不足以支持或反驳 | `VerificationError`；HTTP 错误映射；runner records |
| 12. retry 如何计费与计量？ | 可能再次消耗调用；所有尝试、repair、已知 tokens 都累加。不知道 usage 就标 incomplete，不能根据超时猜零 | `_Budget`、`RunStats`、`resources`、总预算保守预留 |
| 13. scorer 改变后为什么应拒绝 replay？ | 同一原始预测可能被新规则算出另一分数；默认拒绝防止悄悄换评分。旧实验在固定旧代码与锁文件重算 | `SCORING_FILES`、`regenerate_report`；baseline-checks |
| 14. 哪种结果可确定性复算？ | 从冻结 records 计算 strict 分数/固定 seed 区间可复算；重新调用模型有随机性、服务版本/延迟波动，不能保证相同结果 | saved run 与实际 inference 的区别 |
| 15. 谁审了标注？ | 如实说 AI 作者、非作者 AI 首轮是否隐藏 gold、分歧如何裁决；只有本人真正读过并判断的项目才称人类复核 | reviewer 身份、input hash、锁定和裁决记录 |
| 16. 下一步有限资源投入哪里？ | 指向实际错误最多且影响最大的环节，先排除标注/测量错误，再选可验证修复；不能仅因名字叫 optimized 就加复杂度 | dev 失败分类、ablation 代价、真实失败案例 |

## 练习一：合法但不相关的引文

仅在临时练习文件中构造：context 为“版本 2 的批次上限为 8。版本 3 的批次上限为 12。”，claim 为“版本 2 的批次上限为 12。”，模型给 S 并引用第二句。

自己回答：`validate_report` 会不会通过？正确的语义标签是什么？应该引用哪一句？然后通过 Python 调用真正的 `validate_report` 验证第一问，不调用模型。

答案依据：第二句确实存在，所以 literal guard 可以通过；同一个版本 2 的明确上限 8 直接反驳 12，因此应为 C，引用第一句。guard 通过和判断正确是不同命题。

## 练习二：做一条能暴露错误的评分回归

在独立练习副本中写一个小测试：一个 gold 需要两个 passage 的证据——第一段把别名映射到某节点，第二段给该节点的上限。预测只返回第二段的精确引文，断言 `evidence_covered` 为 false；补齐两段应为 true。不要在正式提交上改 scorer。

先确认正确实现的测试通过，再在练习副本临时把“组内全部满足”故意改成“任一满足”。测试必须失败；恢复后再通过。若这个人为缺陷没有让测试失败，说明断言或构造没测到目标。

答案依据：`scoring.evidence_covered` 的 OR-of-AND 语义。核对返回的 quote 本身，而非“它的 index 指到的整段其实含证据”。通过这个练习证明测试能捕捉缺链错误，不只是跟随实现返回值。

## 练习三：解释 C/U 边界

材料只说“启用审计模式时，系统会加签名”。答案说“系统只有启用审计模式才会加签名”。先给 verdict，再写出能使结论改为 S 或 C 的最少新增证据。

答案依据：当前是 U。`A → B` 没有说明 `B → A`，也没有实际反例。增加“关闭审计模式时绝不会加签名”可支持其排他性；增加一次关闭模式却加签名的明确同范围记录可直接反驳它而判 C。不要用你对真实产品实现的印象补条件。
